# データベース仕様書

## 目的

本ドキュメントは、「グランドゴルフしようよ」の現行実装におけるデータ永続化方式（ファイルベースJSONストア）の仕様を示す。

- 要件の一次情報源は `要件定義書.md` である。本書は実装（`src/types/tournament.ts`・`src/lib/store/`・`src/lib/auth/`・`src/lib/service/tournamentService.ts`・`src/lib/domain/validation.ts`・`electron/main.ts`）の内容を記述したものであり、実装を変更した場合は本書も合わせて更新すること。
- API仕様は `API仕様書.md`、画面仕様は `画面仕様書.md` を参照。

## 1. 方式の概要

| 項目 | 内容 |
|---|---|
| 永続化方式 | ファイルベースJSONストア（RDB・DBエンジンは使用しない） |
| 業務データ | `<データ保存先>/db.json` の1ファイルに全テーブル（大会・競技情報・選手・組合せ表・スコア・順位表）を保存する |
| 認証情報 | `<データ保存先>/admin.json`（業務データとは別ファイル） |
| バックアップ | `<データ保存先>/backups/<バックアップID>.json`（1バックアップ＝1ファイル） |
| 読み書き実装 | `src/lib/store/db.ts`（`loadDb()` / `saveDb()` / `updateDb()` / `withDbLock()`）、`src/lib/store/backup.ts`、`src/lib/auth/credentials-store.ts` |
| 業務ルールの担保 | 参照整合性・一意制約・カスケード削除・ブロック系ルールはすべてアプリケーションコード（`src/lib/service/tournamentService.ts`・`src/lib/domain/validation.ts`）で担保する。JSONストア側に制約機構はない |
| 利用可能なランタイム | Node.js runtime（API Route Handlers・Server Components）のみ。ミドルウェア（Edge runtime）からは使用しない |

## 2. データ保存先

### 2.1 保存先ディレクトリの決定

| 実行形態 | 保存先 | 決定箇所 |
|---|---|---|
| 開発（`npm run dev` 等） | 環境変数 `GRANDGOLF_DATA_DIR`。未設定時は `./data`（プロセスのカレントディレクトリ相対） | `src/lib/store/db.ts` の `getDataDir()`、`src/lib/auth/credentials-store.ts` の `getDataDir()` |
| 結合テスト（Playwright） | `.test-data`（`playwright.config.ts` で `GRANDGOLF_DATA_DIR` を指定） | `playwright.config.ts` |
| E2Eテスト（Playwright） | `.e2e-data`（`playwright.e2e.config.ts` で `GRANDGOLF_DATA_DIR` を指定。実行前に初期化） | `playwright.e2e.config.ts`・`tests/e2e/fixtures/env.ts` |
| Electron版 | `electron/main.ts` の `resolveSharedDataDir()` で決定したディレクトリを、Next.jsサーバー子プロセスの環境変数 `GRANDGOLF_DATA_DIR` に設定する | `electron/main.ts` |

Electron版の `resolveSharedDataDir()` は、同一PC内の複数OSユーザーで同じ大会データを共有できるよう、マシン単位の共有ディレクトリを返す。

| OS | 保存先 |
|---|---|
| Windows | `%ProgramData%\グランドゴルフしようよ`（`ProgramData` 未設定時は `C:\ProgramData\グランドゴルフしようよ`） |
| macOS | `/Library/Application Support/グランドゴルフしようよ`（作成に管理者権限が必要なため、初回起動は管理者アカウントで行う） |
| その他（開発用Linux等） | Electron標準のユーザーデータディレクトリ（`app.getPath('userData')`） |

起動時に `ensureDataDir()` でディレクトリを作成（`recursive: true`）し、書き込み可能であることを確認する。失敗した場合はエラーダイアログを表示してアプリを終了する。

### 2.2 保存ファイル一覧

| パス（データ保存先からの相対） | 内容 | 作成・更新契機 | 形式 | 作成元 |
|---|---|---|---|---|
| `db.json` | 業務データ全体（`Db` 型） | 業務データを変更するAPIの実行時、バックアップ復元時 | JSON（インデント2） | `src/lib/store/db.ts` |
| `admin.json` | 管理者のID・パスワードハッシュ | 初回の認証処理時（環境変数からシード）、ID・パスワード変更時 | JSON（インデント2） | `src/lib/auth/credentials-store.ts` |
| `backups/<バックアップID>.json` | バックアップ（メタ情報＋`db.json` の内容） | 手動バックアップ、ログアウト時バックアップ | JSON（インデントなし） | `src/lib/store/backup.ts` |
| `session-secret.json` | セッションCookie署名用の秘密鍵（Electron版のみ） | Electron初回起動時（未作成・破損時は再生成） | JSON（インデント2）、ファイルモード `0o600` | `electron/main.ts` |
| `logs/server.log` | Next.jsサーバー子プロセスの標準出力・標準エラー（Electron版のみ） | Electron起動のたびに上書き（`flags: 'w'`） | テキスト | `electron/main.ts` |

- `db.json` が存在しない場合は空のストア（全コレクションが空配列）として扱う（初期データのシードは行わない）。
- 開発時の `./data`、テスト用の `.test-data`・`.e2e-data` は `.gitignore` 対象。

## 3. 業務データ（db.json）

### 3.1 ストア全体形状

`db.json` は以下の `Db` 型（`src/types/tournament.ts`）に対応する1つのJSONオブジェクトである。トップレベルの各キーがテーブルに相当し、すべて配列である。

```typescript
type Db = {
  tournaments: Tournament[];   // 大会情報
  competitions: Competition[]; // 競技情報（1大会1件）
  players: Player[];           // 選手情報
  parties: Party[];            // 組合せ表（パーティ）
  scores: Score[];             // スコア（選手×ラウンド）
  rankings: RankingSnapshot[]; // 順位表（1大会1件）
};
```

読み込み時は `normalizeDb()` により、欠けている（または配列でない）コレクションを空配列で補う。また `players[].absent` が `true` 以外（未設定を含む）の場合は `false` として読み込む（`absent` は後から追加した項目のため）。各レコードの項目の型・値の検証は読み込み時には行わない。

### 3.2 エンティティ関連

```
Tournament (id)
 ├─ 1:0..1  Competition   (tournamentId)
 ├─ 1:N     Player        (tournamentId)
 ├─ 1:N     Party         (tournamentId, partyNumber)  ── playerIds[] → Player.id
 ├─ 1:N     Score         (tournamentId, playerId, round) ── playerId → Player.id
 └─ 1:0..1  RankingSnapshot (tournamentId)  ── 行の playerId → Player.id（作成時点の写し）
```

- 外部キーは文字列IDの参照であり、DB側での参照整合性チェックはない。
- 「スコア表」は独立したテーブルを持たない。組合せ表（`parties`）×ラウンド数（`Competition.rounds`）から画面上で構成し、保存済みの打数のみを `scores` に持つ。
- 「開始グループ」は保存しない。表示・検証時に `parties` の開始ホールから算出する（`src/lib/domain/pairing.ts` の `assignStartGroups()`）。
- ラウンド合計・総合スコアは保存しない（`scores[].holes` から都度計算する）。順位表のみ作成時点の集計結果をスナップショットとして保存する。

### 3.3 tournaments（大会情報 / `Tournament`）

| 項目 | 型 | 必須 | 制約・備考 |
|---|---|---|---|
| id | string | ◯ | 主キー。作成時に `crypto.randomUUID()` で採番（UUID v4） |
| name | string | ◯ | 大会名。前後空白を除去して保存。1〜50文字（全角・半角を区別せず1文字、サロゲートペアも1文字として数える。`charLength()`） |
| date | string | ◯ | 開催日。`YYYY-MM-DD`（実在する日付）。時刻・タイムゾーンを持たない日付文字列 |
| place | string | ◯ | 開催場所。前後空白を除去して保存。1〜50文字 |
| status | `'進行中'` \| `'終了'` | ◯ | 作成時は `'進行中'`。ステータス切替APIでのみ変更 |
| createdAt | string | ◯ | 作成日時。`new Date().toISOString()`（UTC、ミリ秒まで） |

- 大会名・開催場所の重複は許容する（一意制約なし）。
- 大会一覧は開催日の降順、同日の場合は作成日時の降順で返す（`listTournaments()`）。

### 3.4 competitions（競技情報 / `Competition`）

1大会につき0〜1件。主キーは `tournamentId`（保存時は同じ `tournamentId` の既存レコードを除去してから追加する＝置き換え）。

| 項目 | 型 | 必須 | 制約・備考 |
|---|---|---|---|
| tournamentId | string | ◯ | 大会ID（主キー兼外部キー） |
| rounds | number | ◯ | ラウンド数。整数1〜5 |
| holeInOneConversionEnabled | boolean | ◯ | ホールインワン時のスコア変換（true＝変換あり） |
| holeInOneConversionValue | number \| null | 条件付き | 変換ありの場合のみ必須の整数 -5〜1。変換なしの場合は入力値に関わらず `null` で保存 |
| maxPartySize | number | ◯ | パーティの最大人数。整数1〜6 |
| partyAssignmentMethod | `'チーム'` \| `'シャッフル'` | ◯ | パーティの決定方法 |
| teamBattleEnabled | boolean | ◯ | チーム戦（true＝チーム戦あり） |
| teamRankingMethod | `'合計'` \| `'平均'` \| null | 条件付き | チーム戦ありの場合のみ必須。チーム戦なしの場合は `null` で保存 |

- 数値項目は整数（`Number.isInteger`）であることを要求する。文字列の数値は不可。
- フォームの初期値（`DEFAULT_COMPETITION_FORM`）：ラウンド数1、変換あり、変換値-2、最大人数6、決定方法未選択、チーム戦なし、順位決定方法未選択。
- 競技情報を単独で削除する処理はない（大会削除時のカスケード削除でのみ消える）。

### 3.5 players（選手情報 / `Player`）

| 項目 | 型 | 必須 | 制約・備考 |
|---|---|---|---|
| id | string | ◯ | 主キー。新規登録時に `crypto.randomUUID()` で採番。編集時は既存IDを維持 |
| tournamentId | string | ◯ | 大会ID |
| name | string | ◯ | 選手名。前後空白を除去して保存。1〜10文字。同一大会内で重複不可（前後空白除去後の完全一致で判定。別大会では同名可） |
| birthDate | string | ◯ | 生年月日。入力は `YYYY/MM/DD`（月日は1〜2桁）または和暦 `S/H/R` + `YY.MM.DD`（大文字・小文字可、年月日は1〜2桁）。保存時は西暦 `YYYY-MM-DD` に正規化する。和暦は元号の適用期間外（例：`S64.02.01`）を不正とする（昭和 1926-12-25〜1989-01-07、平成 1989-01-08〜2019-04-30、令和 2019-05-01〜） |
| teamName | string | 条件付き | チーム名。前後空白を除去して保存。0〜10文字。競技情報が「チーム戦あり」または「パーティの決定方法＝チーム」の場合は必須（競技情報未登録の場合は任意）。未入力は空文字列 `''` |
| partyFixed | boolean | ◯ | パーティ固定（true＝固定） |
| partyNumber | number \| null | 条件付き | 固定の場合のみ必須の整数1〜99。非固定の場合は入力値に関わらず `null` で保存 |
| absent | boolean | ◯ | 不参加（true＝不参加）。未指定は `false`。不参加の選手は組合せ表の生成対象・順位表の対象から除外する |
| order | number | ◯ | 登録順。新規は「その大会の既存選手の `order` の最大値＋1」から順に採番、編集時は維持。表示順・チームの並び順に使用 |

- 選手は大会単位の一括保存（`savePlayers()`）でのみ変更する。リクエストに含まれない既存選手は削除扱いとなる。

### 3.6 parties（組合せ表のパーティ / `Party`）

複合キー：`(tournamentId, partyNumber)`。組合せ表生成時に大会単位で一括作成する。

| 項目 | 型 | 必須 | 制約・備考 |
|---|---|---|---|
| tournamentId | string | ◯ | 大会ID |
| partyNumber | number | ◯ | パーティ番号。固定選手のパーティ番号（1〜99）または、固定選手が使用していない番号を1から順に採番した値 |
| startHole | number | ◯ | 開始ホール。整数1〜8。生成時に自動割当（`assignStartHoles()`）、以後パーティ単位で手動変更可 |
| playerIds | string[] | ◯ | 所属選手の `Player.id`（パーティ内の並び順）。空のパーティは保存しない |

- 開始ホールの手動変更では、複数パーティが同じ開始ホールになることを許容する。ただし、対象パーティと同じ開始グループ（変更前）に属する他パーティが使用中の開始ホールは指定できない（4.2参照）。

### 3.7 scores（スコア / `Score`）

複合キー：`(tournamentId, playerId, round)`。

| 項目 | 型 | 必須 | 制約・備考 |
|---|---|---|---|
| tournamentId | string | ◯ | 大会ID |
| playerId | string | ◯ | 選手ID |
| round | number | ◯ | ラウンド番号。整数1〜競技情報のラウンド数 |
| holes | number[] | ◯ | ホール番号1〜8順の打数（開始ホールに関わらず常にホール1→8の順）。要素数ちょうど8、各要素は整数1〜99 |

- 保存されるのは「打数（生の値）」であり、ホールインワン変換後の値ではない。変換（打数1→変換値への置き換え）はラウンド合計の計算時に行う（`src/lib/domain/score.ts`）。
- パーティ×ラウンド単位で、パーティ内全選手分をまとめて保存・削除する。ホール単位・選手単位の部分保存は存在しないため、「一部のホールだけが保存された状態」は発生しない。
- 「試合結果が1件でも登録されている」の判定は、その大会の `scores` が1件以上存在するかどうかで行う（`hasResults()`）。

### 3.8 rankings（順位表 / `RankingSnapshot`）

1大会につき0〜1件（主キーは `tournamentId`。作成・手動確定のたびに既存レコードを置き換える）。「順位表作成」実行時点の集計結果のスナップショットであり、スコア保存時に自動で再集計されない。

| 項目 | 型 | 必須 | 制約・備考 |
|---|---|---|---|
| tournamentId | string | ◯ | 大会ID |
| createdAt | string | ◯ | 順位表作成日時（UTC ISO文字列）。手動確定では更新しない |
| individual | IndividualRankingRow[] | ◯ | 個人戦の順位表（順位順） |
| team | TeamRankingRow[] \| null | ◯ | チーム戦の順位表。チーム戦なし（または順位決定方法未設定）の場合は `null` |
| teamRankingMethod | `'合計'` \| `'平均'` \| null | ◯ | 作成時点のチーム戦の順位決定方法。チーム戦なしの場合は `null` |
| excludedPlayerNames | string[] | ◯ | 全ラウンド分のスコアが揃っておらず集計対象外となった選手名（登録順）。不参加の選手は含めない |

#### IndividualRankingRow（個人戦の行）

| 項目 | 型 | 備考 |
|---|---|---|
| playerId | string | 選手ID |
| playerName | string | 作成時点の選手名 |
| teamName | string | 作成時点のチーム名 |
| totalScore | number | 総合スコア（全ラウンドのホールインワン変換後合計） |
| birthDate | string | 作成時点の生年月日（`YYYY-MM-DD`） |
| rank | number | 順位（同順位あり：1,2,2,4…）。手動確定で上書きされる |
| tieRank | number | 自動集計時点の順位（同順位グループの識別に使用。手動確定でも変わらない） |
| tieSize | number | 自動集計時点の同順位グループの人数 |
| jankenPending | boolean | じゃんけん待ち（同順位グループが2件以上で未確定）かどうか |

#### TeamRankingRow（チーム戦の行）

| 項目 | 型 | 備考 |
|---|---|---|
| teamName | string | チーム名（前後空白除去後）。チーム名が空の選手はチーム戦の集計対象外 |
| memberCount | number | 集計対象となった所属選手数 |
| totalScore | number | 所属選手の総合スコアの合計 |
| averageScore | number | `totalScore / memberCount`（小数のまま保存） |
| totalAgeYears | number | 所属選手の年齢（満年齢）の「年」部分の合計 |
| totalAgeDays | number | 所属選手の年齢の「日」部分の合計（年への繰り上げはしない） |
| totalAgeInDays | number | 所属選手の生後日数の合計（年齢の比較に使用） |
| rank / tieRank / tieSize / jankenPending | number / number / number / boolean | 個人戦と同じ |

- 年齢は大会の開催日を基準日として算出する（`src/lib/domain/age.ts`）。
- 順位決定：個人戦は 総合スコア昇順 → 生年月日が早い順。チーム戦は 合計（または平均。平均は交差乗算で比較）昇順 → 生後日数の合計が大きい順。それでも同じ場合は同順位・じゃんけん待ちとする。

## 4. 業務ルールの担保（アプリケーションコード）

すべて `src/lib/service/tournamentService.ts` に実装されており、1回の更新処理（`updateDb()`）の中で判定・反映を行う。例外が発生した場合は `db.json` を保存しない（部分的な反映は起こらない）。

### 4.1 カスケード削除・連鎖リセット

| 操作 | 連鎖して削除されるデータ |
|---|---|
| 大会の削除（`deleteTournament()`） | 該当大会の `competitions`・`players`・`parties`・`scores`・`rankings` をすべて削除。ステータス（進行中/終了）に関わらず実行可能 |
| 組合せ表の生成・再生成（`generateTournamentPairings()`） | 該当大会の既存 `parties`・`scores`・`rankings` を削除してから新しい `parties` を保存（`resetPairings()`。試合結果がある場合は生成自体を拒否するため、実際に削除される `scores` はない） |
| 競技情報の変更（組合せ表生成済み・試合結果なし・確認済み） | 該当大会の `parties`・`scores`・`rankings` を削除（`resetPairings()`） |
| 選手情報の変更（組合せ表生成済み・試合結果なし・確認済み。選手の追加・削除、選手名・生年月日を含むいずれの項目の変更も対象） | 同上 |
| 試合結果がある状態での（結果のない）選手の削除 | 該当選手を各パーティの `playerIds` から除去し、選手がいなくなったパーティは削除する（組合せ表のリセットは行わない） |

### 4.2 ブロック系ルール

| 対象 | 条件 | 結果（エラーコード） |
|---|---|---|
| 大会情報の更新、競技情報の保存、選手情報の保存、組合せ表の生成、開始ホールの変更、スコアの保存・削除、順位表の作成、最終順位の手動確定 | 大会のステータスが「終了」 | `TOURNAMENT_FINISHED` |
| 競技情報の保存 | 既存の競技情報から1項目でも変更があり、試合結果が1件以上ある | `RESULTS_EXIST` |
| 競技情報の保存 | 既存の競技情報から変更があり、試合結果がなく組合せ表が生成済みで、確認（`confirmReset`）なし | `CONFIRM_REQUIRED`（確認ありなら組合せ表・スコア・順位表を削除して保存） |
| 選手情報の保存 | 試合結果が1件以上あり、削除対象に試合結果のある選手が含まれる | `RESULTS_EXIST` |
| 選手情報の保存 | 試合結果が1件以上あり、既存選手のパーティ固定・パーティ番号・チーム名・不参加のいずれかが変更されている | `RESULTS_EXIST`（選手名・生年月日の訂正、結果のない選手の削除、新規追加は可。いずれも組合せ表・スコアはリセットしない） |
| 選手情報の保存 | 試合結果がなく組合せ表が生成済みで、新規追加・削除、または既存選手の選手名・生年月日・パーティ固定・パーティ番号・チーム名・不参加の変更のいずれかがあり、確認（`confirmReset`）なし | `CONFIRM_REQUIRED`（確認ありなら組合せ表・スコア・順位表を削除して保存） |
| 組合せ表の生成 | 試合結果が1件以上ある | `RESULTS_EXIST` |
| 組合せ表の生成 | 競技情報未登録／参加選手（不参加を除く）が2名未満／固定選手が同一パーティ番号で最大人数超過／（チーム）チーム名未入力の非固定選手あり／（チーム）同一チームの非固定選手が最大人数超過 | `PAIRING_ERROR` |
| 開始ホールの変更 | 同じ開始グループ（変更前）の他パーティが使用中の開始ホールを指定 | `VALIDATION_ERROR` |

- 順位表の作成・手動確定も、「終了」の間は行えない（要件定義書2.1。「終了」前に作成した順位表はそのまま残る）。
- 大会ステータスの切替・大会の削除は、ステータス・試合結果の有無に関わらず実行できる。

### 4.3 一意性

| 対象 | 一意の範囲 | 担保箇所 |
|---|---|---|
| `Tournament.id`・`Player.id` | 全体 | `crypto.randomUUID()` |
| 選手名 | 同一大会内 | `validatePlayerList()`（保存後の全選手一覧で重複検出） |
| `Competition` / `RankingSnapshot` | 1大会1件 | 保存時に同じ `tournamentId` のレコードを除去してから追加 |
| `Party.partyNumber` | 同一大会内 | 組合せ表生成ロジック（`generatePairings()`）での採番 |
| `Score` | `(tournamentId, playerId, round)` | 保存時に同じパーティ・ラウンドの既存スコアを除去してから追加 |

## 5. 日時・日付の保存形式

| 項目 | 形式 | 備考 |
|---|---|---|
| `Tournament.createdAt`・`RankingSnapshot.createdAt`・バックアップの `createdAt` | ISO 8601のUTC日時文字列（`Date.prototype.toISOString()`、例 `2026-11-19T01:23:45.678Z`） | 表示時にアプリ層でAsia/Tokyoへ変換する（`formatDateTimeTokyo()`、`YYYY/MM/DD HH:mm:ss`） |
| `Tournament.date`・`Player.birthDate` | `YYYY-MM-DD`（日付のみ） | タイムゾーン変換の対象外。計算はUTC 0時として行う |

- 外部の日付ライブラリ（date-fns等）は使用せず、`Intl.DateTimeFormat`（`timeZone: 'Asia/Tokyo'`）と自前関数（`src/lib/domain/dates.ts`）で変換する。
- バックアップ履歴の期間絞り込み（`from`/`to`）はAsia/Tokyoの日付として解釈し、UTCの半開区間 `[from 00:00 JST, (to+1日) 00:00 JST)` に変換して比較する（`tokyoDateRangeToUtc()`）。

## 6. 書き込み方式・排他制御

### 6.1 db.json

- **アトミック書き込み**：`saveDb()` は `db.json.<pid>.<timestamp>.tmp` に書き出したのち `rename` で `db.json` に置き換える（書き込み途中のファイルを読まれない）。保存先ディレクトリが無ければ作成する。
- **排他（直列化）**：`withDbLock()` は `globalThis.__ggDbLock` に保持したPromiseチェーンで処理を直列化する（Next.js開発サーバーでルートごとにモジュールが別インスタンスになっても共有されるよう `globalThis` に保持）。同一Node.jsプロセス内でのみ有効で、プロセス間の排他（ファイルロック）は行わない。Electron版は `app.requestSingleInstanceLock()` により二重起動を防いでいる。
- **更新処理**：`updateDb(fn)` は 排他区間内で `loadDb()` → `fn(db)` → `saveDb(db)` を実行する。`fn` が例外を投げた場合は保存しない。
- **参照処理**：一覧・詳細の取得（`loadDb()` 直接呼び出し）はロックを取らない。アトミックな置き換えにより、常にいずれかの完全な状態が読まれる。
- `db.json` が存在しない場合は空のストアを返す。JSONとして不正な場合は例外となる（APIでは `500 INTERNAL_ERROR`）。

### 6.2 admin.json

- `getAdminCredentials()`：`admin.json` を読み込む。存在しない場合は環境変数 `ADMIN_ID`・`ADMIN_PASSWORD` からシードして作成する（どちらかが未設定なら例外）。
- `updateAdminCredentials()`：`writeFile` で直接上書きする（一時ファイル経由のアトミック書き込み・`withDbLock()` による排他は行わない）。

### 6.3 バックアップ

- バックアップの作成・復元は `withDbLock()` の排他区間内で行う。バックアップファイルは `writeFile` で直接書き込む。

## 7. 認証関連データ

### 7.1 admin.json（管理者アカウント）

単一アカウントのみ（配列ではなくオブジェクト1件）。

| 項目 | 型 | 備考 |
|---|---|---|
| id | string | ログインID |
| passwordHash | string | bcryptjs（ソルトラウンド10）でハッシュ化したパスワード。平文は保持しない |

- 初期値は環境変数 `ADMIN_ID`・`ADMIN_PASSWORD`（開発時は `.env.local`）。Electron版は `electron/main.ts` に定義した初期管理者アカウントを子プロセスの環境変数として渡す（`admin.json` が無い初回のみ使用される）。
- 新しいパスワードは8文字以上（API側で検証）。
- `admin.json` はバックアップ・復元の対象外。

### 7.2 セッション

セッションはサーバー側に保存しない。HMAC-SHA256で署名したCookieのみで完結する（`src/lib/auth/session.ts`）。

| Cookie名 | 内容 | 属性 |
|---|---|---|
| `gg_session` | `base64url(JSON{ role, iat }).base64url(HMAC署名)`。`role` は `'admin'` または `'viewer'`、`iat` は発行時刻（エポックミリ秒） | `httpOnly`, `sameSite=lax`, `path=/`。有効期限（`maxAge`/`expires`）は指定しない（ブラウザセッションCookie） |
| `gg_role` | `'admin'` または `'viewer'`（UI表示用。認可判定には使用しない） | `sameSite=lax`, `path=/`（httpOnlyではない） |

- 署名鍵は環境変数 `SESSION_SECRET`。Electron版は `session-secret.json`（初回起動時に `crypto.randomBytes(32)` の16進文字列を生成）から読み込んで子プロセスに渡す。署名鍵が変わると既存のセッションはすべて無効になる。
- `iat` による有効期限チェックは行っていない。

## 8. バックアップ

### 8.1 ファイル形式

`backups/<id>.json` は以下の `BackupFile` 型のJSON（インデントなし）である。

| 項目 | 型 | 備考 |
|---|---|---|
| id | string | バックアップID。`createdAt` の `:` と `.` を `-` に置き換えた文字列＋`-`＋乱数（`Math.random()` の36進表記6文字）。例 `2026-11-19T01-23-45-678Z-k3j9x2`。ファイル名と同じ |
| createdAt | string | 作成日時（UTC ISO文字列、ミリ秒まで） |
| trigger | `'手動'` \| `'ログアウト'` | 作成契機 |
| data | Db | 作成時点の `db.json` の内容（全テーブル：大会・競技情報・選手・組合せ表・スコア・順位表） |

- 対象は業務データ（`db.json`）のみ。`admin.json`・`session-secret.json`・`logs/`・バックアップ履歴自体は含まない。
- バックアップはサーバー側（データ保存先）にのみ保存し、ダウンロード機能は提供しない。

### 8.2 作成・保持数

- 作成（`createBackup()`）：排他区間内で `db.json` を読み込み、バックアップファイルを書き出す。
- 保持数は20件（`MAX_BACKUPS = 20`）。作成後に全バックアップを作成日時の新しい順に並べ、21件目以降（古いもの）のファイルを削除する。
- JSONとして読み込めない（壊れた）ファイルは一覧・保持数の計算から除外される（削除もされない）。

### 8.3 一覧

- `listBackups(from, to)`：`backups/` 配下の `.json` ファイルのメタ情報（`id`・`createdAt`・`trigger`）を作成日時の新しい順に返す。`from`/`to` はAsia/Tokyoの日付（両端を含む）で絞り込む。

### 8.4 復元（リストア）

- `restoreBackup(id)`：`id` が `^[0-9A-Za-z-]+$` に一致しない、またはファイルが読み込めない場合は失敗（API上は `404 NOT_FOUND`）。
- 成功時は、排他区間内でバックアップの `data` を `normalizeDb()` で正規化したうえで `db.json` を**完全に上書き**する（マージはしない）。
- バックアップ履歴（`backups/` 配下）・`admin.json`・セッションは変更しない。復元後も、復元時点より後に作成されたものを含むすべての履歴から再度選択できる。

| 変数名 | 用途 | 既定値 |
